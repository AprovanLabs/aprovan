## Reconciliations (vs the tech plan / tasks, onto the Phases B–D state)

1. **`vfs.commit` no longer skips as unchanged when only a mount moved** — intended per D4, noted as the behavioral consequence of putting mount tokens inside snapshot identity: the "no-op commit" path now creates a commit when upstream moved.
2. **Groups/grant deletion happened in the identity-store world, not the pre-B–D module world.** Tasks 2.1/2.3/4.3 name `groups.ts` + `db/schema.ts`; post-Phases-B–D those are facades over `src/identity/` (interface + Dynamo + relational backends) and two DDLs (`identity/sql.ts` SQLite DDL + `db/dsql-schema.sql`). The excision was applied at all five layers, plus the stream-9 cutover scripts (`snapshot-to-sqlite.ts`, `reseed-dsql.ts`) whose group-tool-grant snapshot/reseed sections would otherwise reference a deleted table, and the identity contract tests (`identity-relational`, `store-backends`, `cutover-reseed`, `groups-dynamodb`).
3. **The "WS-3 resolver" is consumed as storage, not a service.** The workspace reaches profiles through `getRegistryStorage()` (the B–D bindings-cutover seam), so "resolveProfileGrants" is implemented as `grants.grantedProfileIds(tenant, subjects)` — the D12 single indexed join — plus one `profiles.list({targetId})` to map ids → targets (constant two queries, never per-group N+1). `ProfileService.resolveGrantedProfileIds` exists in the package but requires a full `CallContext`/service graph the workspace doesn't construct; the storage-level join is the same query.
4. **Interim dynamo backend degrades explicitly.** Registry-server storage has no Dynamo driver (WS-3 D8), so on `STORE_BACKEND=dynamo` the profile admin surface answers **501** with a pointing message and `profileGrantAllows` resolves to false (group capability requires the relational backend; direct Permissions and admin access work everywhere). Deleting `GroupToolGrants` therefore removes group-grant capability from the interim deploy ahead of the cutover — consistent with the no-compat convention and tech-plan rollout step 4's announce-and-re-attach posture; the whole path dies at the dsql flip.
5. **`mount lineage rides the B–D record-backed VCS** — snapshots/commits live under `svc#vcs#*` records; `mounts`/`provenance` are additive fields on those records (spill-safe via the record store's S3 path), and the legacy-shape test writes/reads through `svc-records` to prove pre-lineage records parse.
6. **Hidden-prefix cache invalidation on publish/remove** (not in tasks): once `hiddenDataPrefixes` feeds *enforcement*, a 30s-stale prefix list would let a just-published app's partitions be read for the TTL window (and broke the new tests via a pre-publish cache prime from the guarded PUT /fs). `saveApp`/`removeApp` now invalidate synchronously.
7. **`/fs-uploads/complete` guarded** (not in tasks): it registers an uploaded blob at an exact path — a write entry point; per the D1 repo-convention note it calls the same guard.
8. **`apps.data` personal semantics tightened**: the pre-existing implementation served personal *records* to any workspace member (membership-gated). Spec D3 wins: personal is rejected outright; the existing `records.test.ts` expectation was inverted accordingly.
9. **Access-tab profile rendering stayed inside `registry-ui`** (task 5.3's Touches): the `CapabilityReach` wire model lives in `@aprovan/ui/apps-store` (core repo — outside this change's two PRs), and `mergeCapabilities` drops unknown fields; `app-detail.tsx` therefore extracts the per-provider `profile` map from the raw `apps.capabilities` response itself and threads it to the provider rows. No core-repo edit required.
10. **Executing-profile name = the provider's stored `default` profile** — the only profile bare app dispatch can resolve (resolution algorithm step 2). When none is stored (zero-config fallback) the field is absent and the client renders the old credential string, which is the ux.md partial state.
11. **Private-section empty state via a remembered root**: an empty partition and an old gateway are indistinguishable from one listing, which ux.md's feature-detection and empty-state requirements otherwise collide on. Once own-partition entries have been seen, the root is remembered per workspace (localStorage) so the section + hint survive emptying; a never-seen partition on an old gateway stays absent.
12. **Commit-detail placement**: the client has no standalone commit-history view; per ux.md's "chat client SessionBar history + `vfs.show` consumers", the Mounted content section hangs off applied chats' `mergeCommit` in the SessionBar Chats dialog (lazy `vfs.show` fetch on expand).

4. **Profile references accept id OR unique name** (`{ profile: string }`): names are unique only per (targetKind, targetId), so an ambiguous bare name answers 400 listing target-qualified candidates rather than guessing. The AdminPanel always sends ids.
5. **`partitionAccess` treats the one-segment path `<hiddenPrefix>/<seg>` as owned by `<seg>`** (protects partition-root paths from foreign create/delete). Consequence: in a `dataScope: "workspace"` app's own publishing workspace, files an app session writes directly at `<root>/data/<file>` are unreadable by *other* members over the raw file plane (they were already invisible in listings); app sessions themselves are unaffected (guard skipped), and installs live in the installer's workspace where no hidden prefix covers them. Judged the safe side of the ambiguity the pure string rule can't resolve.
6. **CDK synth needed `pnpm build` in `infra/` first** (`cdk.json` points at `dist/app.js`) — build-order footnote, no code change.

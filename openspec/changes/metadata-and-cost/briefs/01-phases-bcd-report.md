## WS-3 reconciliations (vs the original tech plan)

1. **Credentials → registry-server, not a workspace `CredentialStoreDsql`** (the brief's mandated reconciliation, replacing tech-plan §5's `credentials` table and task 7.5's store). On `STORE_BACKEND=dsql`, `getCredentialStore()` returns `CredentialStoreRegistry` — an `ICredentialStore` adapter over `@aprovan/registry-server`'s `createSqlStorage(...)` (its `credentials` table already carries `created_by`). The workspace's `db/dsql-schema.sql` deliberately has NO credentials table. The workspace cipher seals payloads (the same envelope the package's own domain layer applies, since WS-3 made the workspace cipher a re-export). `created_by` was still plumbed workspace-side per tech-plan D5: `CredentialInput/Record.createdBy`, populated from the authenticated principal in the create route and CLI, persisted by all three backends (Dynamo attribute, SQLite `created_by` column added in place, registry storage natively).
2. **One cluster, two schemas.** The registry-server DDL and the workspace DDL both name `api_keys` and `audit_log` with different shapes; sharing tech-plan D4's "one database, one schema" verbatim collides. The package's storage therefore lives in a `registry` Postgres schema on the same cluster via a dedicated pool (`SET search_path TO registry, public` per connection), the workspace schema stays in `public` — still one cluster, well under DSQL's 10-schema limit. Found by actually running the gated suites against a Postgres rig, not by inspection.
3. **`fs_latest` two-table shape confirmed** (tech-plan open question 1): `FsStoreDsql` uses `fs_latest` + `fs_files`, mirroring the P#/V# split; no reliance on partial indexes (DSQL-safe).
4. **Regeneration's role shrank because Phase B landed first.** The tech plan's `regenerate-registrations.ts` assumed registrations were `.services` files that die at reseed; post-Phase-B they are records and the reseed carries them. The script now delivers the two halves the spec still needs: re-validation of every registration against its authored source (missing script/entry → reported ISSUE) and the security half — webhook inbound tokens, webhook HMAC secrets, and workflow hook tokens all rotate, with the rotation report for reconfiguring external callers.
5. **Dispatch-plane cutover: bindings half completed, dispatch-route half re-deferred.** The WS-3 blocker (package storage would sit on an ephemeral ECS SQLite in aws mode) is cleared: `src/registry-storage.ts` runs the package's stores on its sqlite driver locally and on the shared IAM-signed DSQL pool in cloud. On those durable backends a workspace interface binding **is** a registry-server profile row (`(tenant, "interface", targetId, name)`; default instance under the package's reserved `"default"`; `sql:analytics` under `"analytics"`), written with the acting user as `created_by`; `.services/bindings.json` is a one-time-import tombstone (read once → imported → deleted), and the only remaining reader of the file is the interim dynamo backend, whose entire code path dies at the `STORE_BACKEND=dsql` flip. NOT done here, deliberately: routing workspace dispatch through `server.dispatch`, deleting the label-as-profile fallback in `resolveCredentialRecord`, and removing colon-syntax instances — the workspace's `sql:analytics` HTTP surface and the aprovan repo's `InterfacesPanel.tsx`/`namespaces.ts` are one product feature, and this PR cannot touch the aprovan repo. Ripping the server side alone would break the shipped UI against this branch. Per the WS-3 report's own sequencing ("cut the workspace onto server.dispatch + package stores and execute 8.4 in the same change" as the product-plane work), that remainder belongs to WS-4/WS-6; the data no longer stands in its way — instances and profiles are now the same rows.
6. **Sequence-prefixed run ids / seq10 keys** carried over the WS-3 convention (lexical order = chronological order) for transcripts, events, and run records.
7. **Interim-backend test pinning:** suites that exercise the Dynamo identity backend (`session.test.ts`, `groups-dynamodb.test.ts`) now pin `STORE_BACKEND=dynamo`, since the local default became the relational SQLite backend.

## Deviations

1. **Dispatch-route half of the WS-3 cutover re-deferred** — reconciliation #5 above; the honest blocker now is the cross-repo product surface, not storage durability.
2. **`AWS::DSQL::Cluster` is an L1 `CfnResource` by type** — aws-cdk-lib 2.180.0 ships no `aws-dsql` module; endpoint derived as `<identifier>.dsql.<region>.on.aws`. Upgrade to the typed construct when the repo bumps CDK.
3. **`prefixGrants` on relational backends refuse writes** (`GroupPrefixGrants` not carried, per spec); the Dynamo backend keeps today's behavior until cutover so the admin surface keeps working on the interim deploy. WS-6 removes the surface.
4. **API keys**: implemented on the relational backends per tech-plan §4 (`create/list/verify/revoke`, `apw_` prefix, plaintext-once); the Dynamo backend refuses `create` (no implementation ever existed workspace-side, and building one for a backend that retires at cutover would be waste).
5. **`WorkflowRegistration.script`** (inline source) added so sync's generated companion runners are state, not `.services` files — the one interface extension beyond the tech plan, internal to the workspace.
6. **`limits.budget`-style semantics untouched**; profile *resolution* (grants, stored-default rules) remains registry-server's — this change only made its storage the workspace's system of record for bindings.
7. **Internal record scopes predating this change** (`telemetry`, `notify`, `leader`, `sandboxops`) keep their bare scope names: they were never `.services` files and are unreachable from caller scopes; renaming them under `svc#` would have churned fixtures for no isolation gain. The sandbox queue moved (`sandboxqueue` → `svc#sandboxes#queue`) because its run history moved with it.
8. **`docker/registry.Dockerfile` smoke and `pnpm -r test` were not re-run** (not in this brief's Verify); the workspace suite + typecheck + infra synth are the specified gates.
9. **Test-rig containers**: the DSQL-gated suites were validated against a scratch `postgres:16` container (since torn down); CI should point `WORKSPACE_TEST_DSQL_URL` at the dev DSQL cluster per tech-plan open question 2.

## OWNER RUNBOOK (production cutover — full detail in `registry/docs/cutover-runbook.md`)

Rehearse everything on dev first and record timings; the prod read-only window is sized from that rehearsal. Stop at any non-zero exit.

1. **Preconditions** — DSQL cluster deployed (this PR's default synth creates it dark); gated suites green against the dev cluster:
   `WORKSPACE_TEST_DSQL_URL=<dev url> pnpm --filter @aprovan/workspace exec vitest run tests/store-backends.test.ts` → expect `14 passed`, 0 skipped. Phase-B migration sweeps run everywhere: `tsx scripts/migrate-services-to-records.ts --workspace <id> --all`.
2. **Read-only window** — announce; hold the service at one task (`aws ecs update-service … --desired-count 1`); post-snapshot writes are dropped by decision.
3. **Snapshot** — `FS_BUCKET=… FS_TABLE=… RECORDS_TABLE=… CREDENTIALS_TABLE=… tsx scripts/snapshot-to-sqlite.ts --out /tmp/cutover-mirror` → `Snapshot complete:` + per-table counts (record them). Resumable — re-run on interruption.
4. **Verify** — `tsx scripts/verify-snapshot.ts --data /tmp/cutover-mirror` → all `[PASS]` + `Snapshot verification passed.`; any `[FAIL]`/exit 1 = STOP. Archive the mirror (rollback of last resort).
5. **Reseed** — `DSQL_ENDPOINT=… AWS_REGION=… tsx scripts/reseed-dsql.ts --from /tmp/cutover-mirror` → `Reseed complete:` with counts matching step 3 (fsLatest == fsFiles etc.). Refuses on >900-byte paths (fix, re-snapshot, re-verify). Idempotent; S3 blobs untouched; credentials land in the registry schema with `created_by = "reseed:unknown"` where unowned.
6. **Regenerate** — `tsx scripts/regenerate-registrations.ts --workspace <each id>` → per-registration `ok`/ISSUE lines and the **webhook secret rotation report**; reconfigure every external caller with the fresh tokens/HMAC secrets before ending the window.
7. **Flip** — `cd infra && pnpm cdk deploy -c storeBackend=dsql` (sets `STORE_BACKEND=dsql`; Dynamo tables untouched).
8. **Observe** — `/health` 200; tree/contents/records/credentials/memberships intact; version history empty and audit empty by design; watch for sustained `serialization failure` retry storms. Then end the window. **Rollback:** redeploy without the context flag (back to dynamo, tables never touched); last resort: boot `WORKSPACE_MODE=local WORKSPACE_DATA_DIR=<mirror>`.
9. **Cleanup (separate deploy, after confirmation — suggested ≥1 week)** —
   `pnpm cdk diff -c storeBackend=dsql -c dynamoRetired=true` (review), then `pnpm cdk deploy -c storeBackend=dsql -c dynamoRetired=true`. Verify first with `pnpm cdk synth -c storeBackend=dsql -c dynamoRetired=true --quiet && grep -c '"AWS::DynamoDB::Table"' cdk.out/*.template.json` → expected `0`. Removes the 11 registry-stack tables + PITR + grants + env and the core identity-table imports/grants; FS bucket, KMS key, DSQL cluster remain. The core Users/Workspaces/Memberships/Invites tables then retire in the aprovan core stack once nothing references them. Guardrail: `dynamoRetired=true` without `storeBackend=dsql` refuses to synth.
